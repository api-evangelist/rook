<figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*GkD6TK_y9COmgRX-0djiuA.png" /></figure><p>The <a href="https://github.com/rook/rook/releases/tag/v1.14.0">Rook v1.14</a> release is out! v1.14 is another feature-filled release to improve storage for Kubernetes. Thanks again to the community for all the great support in this journey to deploy storage in production.</p><p>The statistics continue to show Rook community growth since the <a href="https://blog.rook.io/rook-v1-13-storage-enhancements-c551f62892bb">v1.13 release</a> in December:</p><ul><li>11.6K to 11.9K <a href="https://github.com/rook/rook/stargazers">Github stars</a></li><li>304M to 317M Container downloads</li><li>6.4K to 6.6K <a href="https://slack.rook.io/">Slack</a> members</li><li>7.3K to 7.5K <a href="https://x.com/@rook_io">X</a> followers</li></ul><p>We have a lot of new features for the Ceph storage provider that we hope you’ll be excited about with the <a href="https://github.com/rook/rook/releases/tag/v1.14.0">v1.14 release</a>!</p><h3>Versions</h3><h4>Ceph Squid Support</h4><p>Ceph Squid (v19) is the next major version of Ceph that is set to be released in the next month. Keeping up with the latest updates to the data plane is critical to Rook so you can always deploy the version of the data plane that you desire. To learn more about the new features in the Squid release, see the <a href="https://github.com/ceph/ceph/blob/squid/PendingReleaseNotes">pending release notes</a>.</p><p>In addition to Squid, Rook v1.14 continues to support Quincy (v17) and Reef (v18). In Rook v1.15 we anticipate removing support for Quincy to correspond with its end-of-life from the Ceph team. If you are still running Quincy, we encourage you to <a href="https://rook.github.io/docs/rook/v1.13/Upgrade/ceph-upgrade/">update</a> to the <a href="https://docs.ceph.com/en/latest/releases/#active-releases">latest version of Reef</a> in the near future.</p><h3>Kubernetes v1.25+</h3><p>Kubernetes v1.25 is now the minimum version supported by Rook, which means we run CI tests against v1.25 and newer. If you still require running an older K8s version we haven’t done anything to prevent running Rook, we simply just do not have test validation on older versions.</p><h3>Object Stores</h3><h4>DNS Subdomain Style Bucket Names</h4><p>The <a href="https://rook.io/docs/rook/v1.14/CRDs/Object-Storage/ceph-object-store-crd/#hosting-settings">hosting settings</a> allow hosting buckets in the object store on a custom DNS name, enabling virtual-hosted-style access to buckets similar to <a href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/VirtualHosting.html">AWS S3</a>. When the expected DNS names are added to the CephObjectStore, the virtual style host names will be enabled. The default object store service DNS entry is enabled automatically for Ceph Reef or newer.</p><h4>Shared Pools for Multiple Object Stores</h4><p>Until now, Rook has configured object stores each with their own metadata and data pools. When multiple object stores were desired for data isolation, this resulted in many pools being created and caused challenges with PG management. Now, as a significant improvement for object store scalability, multiple object stores can be created <a href="https://rook.io/docs/rook/v1.14/Storage-Configuration/Object-Storage-RGW/object-storage/#create-local-object-stores-with-shared-pools">with the same underlying metadata and data pools</a>. This means object stores can scale out while maintaining the same two pools and a constant set of PGs. Isolation between the object stores is provided by RADOS namespaces for each of the object stores.</p><p>By default, object stores will still create separate pools. In the future, we expect the shared pools to become the default mode for creating new object stores.</p><h3>Security</h3><h4>Default Service Account</h4><p>With v1.14, all pods started by Rook will be configured with a custom service account instead of relying on the default service account for some pods. Ceph daemons including the mon, mgr, and rbd mirror were previously using the default service account. Now these daemons will be configured with a new service account named rook-ceph-default. There are not any new privileges added to this service account, but it allows more explicit control of the service accounts. For example, if <a href="https://rook.io/docs/rook/v1.14/Getting-Started/Prerequisites/authenticated-registry/">authenticated container registries</a> are configured, the new service account will also require configuration.</p><h4>Azure Key Vault</h4><p>In addition to other <a href="https://rook.io/docs/rook/latest/Storage-Configuration/Advanced/key-management-system/">KMS providers</a>, support for <a href="https://rook.io/docs/rook/latest/Storage-Configuration/Advanced/key-management-system/#azure-key-vault">Azure Key Vault</a> was added for storing OSD encryption keys. If OSDs are to be encrypted and you have a cluster configured in the Azure cloud, consider configuring your clusters with encrypted OSDs for greater security.</p><h3>Ceph-CSI v3.11</h3><p>The <a href="https://github.com/ceph/ceph-csi/releases/tag/v3.11.0">v3.11 release</a> of the Ceph-CSI driver is now the version deployed by default with Rook. The driver has a number of important updates to add more storage features and fixes available to clients. The primary features to mention are:</p><ul><li>VolumeSnapshotGroup support has been added to both the RBD and CephFS CSI drivers.</li><li>Azure Key Vault support for both RBD and CephFS drivers.</li></ul><h3>Network</h3><h4>Holder Pod Deprecation</h4><p>Rook is beginning the process of deprecating holder pods. The holder pod was previously required for scenarios where host networking was disabled in the CSI driver, including Multus. After reviewing user feedback and available options, we have determined the preferred option for the CSI driver is to use host networking instead of holder pods. Clusters that have enabled the holder pods with Multus or similar configuration will need to follow the migration guide to disable the holder pods soon. We understand this can be a significant configuration change, so the holder pods are still supported in v1.14 to give you time to transition. See the documentation for <a href="https://rook.io/docs/rook/latest/CRDs/Cluster/network-providers/#modifying-csi-networking">details on the migration</a>.</p><h3>Kubectl Plugin</h3><p>Rook’s <a href="https://github.com/rook/kubectl-rook-ceph">Kubectl plugin</a> continues to be a tool where we are investing to improve troubleshooting scenarios. Since the Rook v1.13 release, we have released both v0.7 and v0.8 plugin versions. These releases include several features and bug fixes:</p><ul><li>List and cleanup stale subvolumes</li><li>Cleanup test clusters</li><li>Internally use K8s dynamic API instead of kubectl</li></ul><p>We look forward to your feedback on other commands that will help you maintain and troubleshoot your clusters!</p><h3>What’s Next?</h3><p>As we continue the journey to develop reliable storage operators for Kubernetes, we look forward to your ongoing feedback. Only with the community is it possible to continue this fantastic momentum.</p><p>There are many different ways to get involved in the Rook project, whether as a user or developer.
