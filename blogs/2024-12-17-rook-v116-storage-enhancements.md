<figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*3U1FfFVsoeXvWzt9IKeFXw.png" /></figure><p>The <a href="https://github.com/rook/rook/releases/tag/v1.16.0">Rook v1.16</a> release is out! v1.16 is another feature-filled release to improve storage for Kubernetes. Thanks again to the community for all the great support in this journey to deploy storage in production.</p><p>The statistics continue to show Rook community growth since the <a href="https://blog.rook.io/rook-v1-15-storage-enhancements-6f0d6a795601">v1.15 release</a> in August:</p><ul><li>12.2K to 12.5K <a href="https://github.com/rook/rook/stargazers">Github stars</a></li><li>333M to 337M Container downloads</li><li>6.8K to 7.1K <a href="https://slack.rook.io/">Slack</a> members</li><li>7.7K to 7.9K <a href="https://x.com/@rook_io">X</a> followers</li></ul><p>We have a lot of new features for the Ceph storage provider that we hope you’ll be excited about with the <a href="https://github.com/rook/rook/releases/tag/v1.16.0">v1.16 release</a>!</p><h3>Object Stores</h3><p>One of the themes the Rook team has been seeing for a while is an expanding set of advanced object store use cases. This Rook release focuses heavily on expanding object store options and flexibility.</p><h4>Multiple Instances</h4><p>Multiple object stores can now be configured to be backed by the same pools. There are various configurations that can be unique between the object stores:</p><ul><li>Hosting and gateway configurations on different ports and domains</li><li>Different protocols to support S3, Swift, and/or Admin-Ops</li><li>Resources and limits unique per RGW instance</li></ul><p>This feature helps significantly increase the flexibility of the object stores. See the <a href="https://rook.io/docs/rook/v1.16/Storage-Configuration/Object-Storage-RGW/object-storage/#object-multi-instance">multi-instance documentation</a> for more details on configuring these options.</p><h4>S3 Bucket Policy</h4><p>Object Bucket Claims can specify a bucket policy for the S3 bucket. The policy is applied with the <em>additionalConfig.bucketPolicy</em> field. The policy is specified as a JSON blob and supports all bucket policy that the Ceph RGW supports.</p><h4>Arbitrary Object Store Configuration</h4><p>Rook always seeks to maintain a well-designed and well-tested feature set. Maintaining this high quality at a pace that meets users has been a challenge. To help address a broad range of new features for CephObjectStore users wanting to push the limits of their object store, Rook has introduced two mechanisms for advanced configuration of Rook’s RGW daemons.</p><ol><li>Set arbitrary RGW <a href="https://rook.io/docs/rook/v1.16/CRDs/Object-Storage/ceph-object-store-crd/#advanced-configuration">config and commandline flag values</a></li><li>Add arbitrary Pod volume mounts to the RGW pod with <a href="https://rook.io/docs/rook/v1.16/CRDs/Object-Storage/ceph-object-store-crd/#example-usage-with-additionalvolumemounts"><em>additionalVolumeMounts</em></a></li></ol><p>The Rook team is excited to see what users are able to accomplish with the freedom afforded by these options. We also encourage users to share their uses with us and contribute suggestions that other users might benefit from.</p><h4>RGW Operation Logging</h4><p>By default, all RGW logs are included in the main RGW container logs. For enhanced observability of the operations, the RGW operations logs can be separated from the main RGW container logs. This is enabled by a sidecar with the <em>opsLogSidecar</em> setting found under the <a href="https://rook.io/docs/rook/v1.16/CRDs/Object-Storage/ceph-object-store-crd/#gateway-settings">gateway settings</a>.</p><h4>Bulk Data Pool</h4><p>The object store data pool is now marked as <em>bulk: true</em> by default. This flag enables the full set of PGs to be created immediately instead of growing over time as the PG autoscaler might determine. Since the data pool for an object store is expected to be large, PG placement will be better optimized with this flag.</p><h3>Ceph CSI v3.13</h3><p>The latest Ceph-CSI release has a number of features and improvements, including:</p><ul><li>Volume group snapshots for RBD volumes</li><li>CephFS support for the omap data store in rados namespaces</li></ul><h3>OSDs Replacement</h3><p>While many settings are configurable at runtime on OSDs with Ceph settings, some OSD settings are immutable. For example, encryption cannot be enabled or disabled on the OSD after it is created. The only way to change such settings is by purging the OSD, wiping the device, creating a new OSD in its place, and waiting for the data to backfill.</p><p>The OSDs can be replaced by updating the desired settings, then setting the value <em>storage.migration.confirmation: yes-really-migrate-osds</em> in the CephCluster CR. Rook will then automating replacing the OSDs one by one. See the <a href="https://rook.io/docs/rook/v1.16/Storage-Configuration/Advanced/ceph-osd-mgmt/#osd-migration">OSD migration documentation</a> for more details.</p><h3>RADOS Namespace Mirroring</h3><p>RADOS namespaces can be mirrored across clusters, similar to mirroring a pool or RBD image. Enable the RADOS namespace mirroring with the <em>mirroring</em> settings in the <a href="https://rook.io/docs/rook/v1.16/CRDs/Block-Storage/ceph-block-pool-rados-namespace-crd/#mirroring">CephBlockPoolRadosNamespace CR</a>. This feature is experimental as it requires Ceph Tentacle (v20), which is not planned for release until some time in 2025.</p><p>If the <em>statusCheck</em> is enabled on the parent CephBlockPool, the status of the RADOS namespace mirroring will be updated periodically in the status field of the CephBlockPoolRadosNamespace CR.</p><h3>Versions</h3><h4>Ceph Quincy Support Removed</h4><p>Ceph Quincy v17 has reached end of life and is no longer supported by the Ceph team. Rook has removed support for Quincy in this release. Clusters must be upgraded to at least Reef v18 before upgrading to Rook v1.16. Rook continues to support Reef v18 and Squid v19.</p><h4>Kubernetes v1.27 - v1.32</h4><p>Kubernetes v1.27 is now the minimum version supported by Rook through the latest K8s release v1.32, which means we run CI tests against v1.27 through v1.32. If you still require running an older K8s version we haven’t done anything to prevent running Rook, we simply just do not have test validation on older versions.</p><h3>What’s Next?</h3><p>As we continue the journey to develop reliable storage operators for Kubernetes, we look forward to your ongoing feedback. Only with the community is it possible to continue this fantastic momentum.</p><p>There are many different ways to get involved in the Rook project, whether as a user or developer.
