<figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*ZcQMwUs_yMwrfsgVbP11hQ.png" /></figure><p>The <a href="https://github.com/rook/rook/releases/tag/v1.17.0">Rook v1.17</a> release is out! v1.17 is another feature-filled release to improve storage for Kubernetes. Thanks again to the community for all the great support in this journey to deploy storage in production.</p><p>The statistics continue to show Rook is widely used in the community:</p><ul><li>12.7K <a href="https://github.com/rook/rook/stargazers">Github stars</a></li><li>341M Container downloads</li><li>7.3K <a href="https://slack.rook.io/">Slack</a> members</li><li>7.9K <a href="https://x.com/@rook_io">X</a> followers</li></ul><p>We have a lot of new features for the Ceph storage provider that we hope you’ll be excited about with the <a href="https://github.com/rook/rook/releases/tag/v1.17.0">v1.17 release</a>!</p><h3>Object Stores</h3><h4>ObjectBucketClaims secure by default</h4><p>Several ObjectBucketClaim options were added previously in Rook v1.16 that allowed more control over buckets. These controls allow users to self-serve their own S3 policies. Administrators may consider this flexibility a risk, depending on their environment. Rook now disables these options by default to ensure the safest off-the-shelf configurations.</p><p>To enable the full range of OBC configurations, the new setting `ROOK_OBC_ALLOW_ADDITIONAL_CONFIG_FIELDS` must be set to enable users to set all of these options. For more details, see the <a href="https://rook.io/docs/rook/v1.17/Storage-Configuration/Object-Storage-RGW/ceph-object-bucket-claim/#obc-custom-resource">OBC additionalConfig documentation</a>.</p><h4>CephObjectStoreUser Credential Management</h4><p>Rook has added first-class credential management to CephObjectStoreUser resources, allowing multiple credentials and declarative credential rotation. For more details, see <a href="https://rook.io/docs/rook/v1.17/Storage-Configuration/Object-Storage-RGW/object-storage/#managing-user-s3-credentials">Managing User S3 Credentials</a>.</p><p>As a result, existing S3 users provisioned via CephObjectStoreUser resources no longer allow multiple credentials to exist on underlying S3 users, unless explicitly managed by Rook. Rook will purge all but one of the undeclared credentials. This could be a user observable regression for administrators who manually edited/rotated S3 user credentials for CephObjectStoreUsers, and affected users can make use of the new credential management feature as an alternative.</p><h4>Bucket Owner</h4><p>The name of a pre-existing Ceph RGW user account can be set as the bucket owner on an ObjectBucketClaim (OBC), rather than a unique RGW user being created for every bucket. A <em>CephObjectStoreUser</em> resource may be used to create the Ceph RGW user account which will be specified on the OBC. If the bucket owner is set on a bucket that already exists and is owned by a different user, the bucket will be re-linked to the specified user.</p><h4>Kafka auth mechanism</h4><p>Ceph recently added support for configuring which authentication mechanism to use for bucket notifications using Kafka topics. This can be configured by setting the <em>mechanism</em> field of the Kafka section of the bucket notification.</p><h3>CSI</h3><h4>Ceph CSI 3.14</h4><p>The Ceph CSI release has a number of features and improvements for RBD and CephFS volumes, volume snapshots, and many more areas. See the <a href="https://github.com/ceph/ceph-csi/releases/tag/v3.14.0">Ceph CSI 3.14 release notes</a> for more details.</p><h4>Ceph CSI Operator</h4><p>The Ceph CSI operator is an active area of development and we have decided to keep the feature in experimental mode in this release. To ensure feature compatibility and have full confidence in the testing, we will wait until Rook v1.18 to enable it by default. This additional time to test will help ensure a smooth transition from Rook’s CSI driver orchestration to the CSI operator.</p><p>Until then, we encourage you to help us validate the CSI operator by enabling it in a test cluster with two simple steps:</p><ol><li>Install the CSI operator with <a href="https://github.com/rook/rook/blob/master/deploy/examples/csi-operator.yaml">csi-operator.yaml</a>. This will create the necessary Ceph-CSI Operator CRDs and start the new operator.</li><li>Enable Rook to use the CSI operator by setting <em>ROOK_USE_CSI_OPERATOR: “true” </em>in the <em>rook-ceph-operator-config</em> configmap</li></ol><p>Rook will then automatically create the needed CRs to configure the Ceph CSI operator. Please let us know if you have any feedback on the new CSI configuration!</p><h3>Mon Endpoints</h3><h4>External Mons</h4><p>In some two-datacenter clusters, there is no option to start an arbiter mon in an independent K8s node to configure a proper <a href="https://rook.io/docs/rook/v1.17/CRDs/Cluster/stretch-cluster/">stretch cluster</a>. The external mons now allow a mon to be configured outside the Kubernetes cluster, while Rook manages everything else inside the cluster. For more details, see the <a href="https://rook.io/docs/rook/v1.17/Storage-Configuration/Advanced/ceph-mon-health/#external-monitors">External Mon documentation</a>. This feature is in currently in experimental mode.</p><h4>DNS Resolution for Mons</h4><p>On occasion, the list of mons may change when there is a <a href="https://rook.io/docs/rook/v1.17/Storage-Configuration/Advanced/ceph-mon-health/#failing-over-a-monitor">mon failover</a> during a network or other outage. The CSI driver automatically handles this for the volumes inside the K8s cluster. Now dynamic DNS resolution allows clients outside the K8s cluster to resolve mon endpoints via DNS without requiring manual updates to the list of mon endpoints. This helps in scenarios such as virtual machine live migration. The Ceph client can connect to rook-ceph-active-mons.&lt;namespace&gt;.svc.cluster.local to dynamically resolve mon endpoints and receive automatic updates when mon IPs change. To configure this DNS resolution, see <a href="https://rook.io/docs/rook/v1.17/Storage-Configuration/Advanced/ceph-mon-health/#tracking-mon-endpoints">Tracking Mon Endpoints</a>.</p><h3>Ceph Config</h3><h4>Node specific node.conf overrides</h4><p>The <a href="https://rook.io/docs/rook/latest-release/Storage-Configuration/Advanced/ceph-configuration/#custom-cephconf-settings">ceph.conf overrides</a> can now be customized per-node. This may be helpful for some ceph.conf settings that need to be unique per node depending on the hardware. This can be configured by creating a node-specific configmap that will be loaded for all OSDs and OSD prepare jobs on that node, instead of the default settings that are loaded from the <em>rook-config-override</em> configmap.</p><p>The node-specific configmaps must have the label:<br />node.config.rook.io/osd</p><p>The configmaps must follow the naming convention:<br />rook-config-override-&lt;hostname&gt;</p><h3>Versions</h3><h4>Kubernetes v1.28 — v1.33</h4><p>Kubernetes v1.28 is now the minimum version supported by Rook through the latest K8s release v1.33 (to be released any day now). Rook CI runs tests against these versions to ensure there are no issues as Kubernetes is updated. If you still require running an older K8s version, we haven’t done anything to prevent running Rook, we simply just do not have test validation on older versions.</p><h3>What’s Next?</h3><p>As we continue the journey to develop reliable storage operators for Kubernetes, we look forward to your ongoing feedback. Only with the community is it possible to continue this fantastic momentum.</p><p>There are many different ways to get involved in the Rook project, whether as a user or developer.
